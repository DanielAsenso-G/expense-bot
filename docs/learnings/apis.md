# APIs & HTTP

Before this, "API" was a word I used without really having a picture for it. The one that finally worked was a menu. When my code talks to Telegram, I don't get to reach into their servers and poke around — I order from a fixed list of things they let me ask for (send a message, fetch updates, set a webhook), in exactly the format they specify. That menu *is* the API: a contract between two programs, where one side exposes a set of requests and keeps everything behind them hidden. Once I noticed every call follows the same shape — `https://api.telegram.org/bot<token>/<method>` — the whole thing felt a lot less like magic.

What took longer to sink in was that "client" and "server" aren't fixed labels; they're roles that swap depending on who starts the conversation. When my bot sends a message, it's the client calling Telegram's server. When Telegram pushes a message to my bot, Telegram is the client and my code is the server. Same two parties, opposite roles, depending on which way the request is flowing.

GET and POST confused me for a while, because I assumed the type was somehow worked out from what the request did. It isn't. It's just a word the sender writes at the start of the request — GET if you're reading something, POST if you're sending data along in the body. And that's a convention, not a rule the machine enforces: Telegram will happily let you "set" a webhook with a GET even though it clearly changes something. That bugged me until I accepted that the label is just the sender's declaration, nothing more.

The last piece was realising a response is really two things: a status code and a body. The code is a quick summary of how it went — 200 fine, 403 not allowed, 404 nothing at this address, 422 you sent something malformed, 500 it broke — and the body is the actual content that comes back. A 404 stopped feeling like "broken" once I understood it just means the server is alive and simply has nothing at the address I asked for.
